### 1. 【大模型基础】直接使用大模型有什么问题？智能体包含哪四个能力？

**答案**

直接使用大模型有四个弊端：

1. **数据不及时**——大模型的训练数据有截止时间，最新的联网搜索也不是大模型本身的能力。
2. **专业领域知识缺失**——市面上的大模型基本都是通用大模型，专业领域或企业内部数据它不知道。
3. **无法直接调用外部工具**——查时间、查天气、订票这类事它做不到。
4. **多次对话没有记忆功能**——新开一个对话，之前说过的身份、背景全部丢失。

智能体的四个关键能力：

1. **感知**——从环境中获取信息的能力。
2. **执行**——通过执行器把决策转化为实际行为，对环境产生影响。
3. **思考推理与决策**——智能体的大脑，根据感知信息和自身知识进行分析、规划、判断。
4. **记忆学习与适应**——根据历史经验改进未来的决策，在变化环境中更好达成目标。

可归纳为：**AI Agent = 大模型 + 记忆 + 感知数据 + 调用工具行动**。

**解析**：企业不直接调用大模型，而是把大模型当作"聪明但没有记忆、没有手脚的大脑"，再补上记忆（知识库）、手脚（插件）、感知（输入数据），这个整体就是智能体。

**出处**：第1章-01-智能应用开发的介绍 → 1.4.1 企业中是如何使用大模型的、1.4.2 什么是智能体

### 2. 【大模型基础】大语言模型、推理模型、多模态模型、全模态模型的区别？能上传图片就一定是多模态模型吗？

**答案**

| 类型 | 定义 | 关键特征 |
|---|---|---|
| 大语言模型（LLM） | 只能处理文本数据的大模型 | "直进直出"的概率预测，预测下一个字，并非真正理解逻辑；复杂任务易逻辑断裂或幻觉 |
| 推理大模型 | 在传统大语言模型基础上，强化推理、逻辑分析和决策能力的模型 | 支持多步逻辑推导、链式思维（先输出中间推理步骤再给结论）；上下文理解与复杂关系推理更强 |
| 多模态大模型 | 能处理**两种及以上**类型数据（文本、图片、音频、视频等）的模型 | 能"看懂"图片、生成图片，而不只是读文字 |
| 全模态大模型 | 能处理**所有**类型数据的模型 | 模态覆盖最完整 |

**能上传图片，不一定是多模态模型。**

反例是 DeepSeek：它能接收图片，但获取的是**图片上的文字**（本质是 OCR 文字提取），从底层看仍然只处理文本，并不像真正的多模态模型那样看懂图片内容、生成图片。所以课件明确判定 DeepSeek 属于**大语言模型**。

**解析**：判断标准不是"能不能传图片"，而是"模型原生处理的模态数量"。传图片后只留下文字，模态并没有增加。

**出处**：第1章-04-AI基础知识 → 4.1.1 大语言模型、4.1.2 推理大模型、4.1.3 多模态/全模态大模型（含 DeepSeek 课堂提问）

### 3. 【大模型基础】"温度"（Temperature）参数影响什么？要生成更严谨、确定的代码该调高还是调低？

**答案**

温度（Temperature，T）调整生成结果的**随机性**，范围通常是 0~2。

- **低温（T < 1，如 0.2）**：让高概率的"好答案"概率更高、低概率的更低，模型变得保守、确定，几乎总是选概率最高的词。适合**代码生成、数学推理、事实问答**等需要精准的任务。
- **高温（T > 1，如 1.5）**：拉平概率分布，所有选项概率更接近，模型更冒险，输出创意多变但可能逻辑混乱。适合写诗、头脑风暴、虚构故事。
- **温度 = 1**：保持模型原始概率分布，是平衡点。

**希望生成的代码更严谨、确定，应把温度调低**（例如 0.2，对应平台上的"精确模式"）。

**解析**：大模型是按概率随机选词的，温度就是"选词策略"的旋钮。温度越低越倾向于只选最高概率词，输出越稳定可复现。

**出处**：第3章-03-智能体常见的设置 → 3.3.3.3 生成随机性（温度）

### 4. 【提示词】提示词的五大原则分别是什么？

**答案**

基于 OpenAI 官方文档提炼的五条大原则：

1. **清晰的指令**
2. **文本参考**（提供参考资料/示例）
3. **复杂任务拆分为简单子任务**
4. **给模型"思考"的时间**
5. **借助外部工具**

其中"清晰的指令"有 5 个具体做法：**详细描述、扮演角色、使用分隔符、提供示例、指定长度**。

**解析**：任何 Prompt 技巧都不如把需求表达清楚。复杂任务要像剥洋葱一样一层层拆解；数学类问题要让模型写出"计算过程"；该联网就联网、该写代码就写代码。

**出处**：第2章-02-提示词（重点） → 2.2.2 提示词工程的五大原则、2.3 本章小结

### 5. 【JSON】JSON 支持哪六种数据类型？键值对之间的分隔符是什么？

**答案**

六种数据类型：

| 类型 | 示例 | 说明 |
|---|---|---|
| 字符串 String | `"Hello"`、`"张三"` | 一段文本，可写任意内容，如姓名、邮箱 |
| 数字 Number | `123`、`3.14` | 不加引号，支持整数和小数，如年龄、身高 |
| 布尔值 Boolean | `true`、`false` | 必须全小写，不能写 True/False |
| 空值 Null | `null` | 必须全小写，不能写 NULL；用户未输入即 null |
| 对象 Object | `{ }` | 描述现实复杂事物的数据结构 |
| 数组 Array | `["唱歌","跳舞","篮球"]` | 一组相同类型数据的容器，用方括号包裹 |

**键值对之间的分隔符是英文逗号 `,`**。

补充区分（容易混）：
- 键和值之间用**英文冒号 `:`**
- 键必须用**英文双引号**包裹
- **最后一组数据后面不加逗号**

**出处**：第3章-03-智能体常见的设置 → 3.5.3 JSON 的编写规则

### 6. 【JSON】为什么数据交互通常用 JSON 而不是纯文本？文本传递有什么弊端？

**答案**

**纯文本传递的弊端**：

1. **数据全部挤在一起，无法区分**。例如注册信息用纯文本传过去是：
   `zhangsan123456zhangsan@126.com张三13112345678男20260530111`
   后端的开发者根本分不清哪一段是用户名、哪一段是手机号。
2. **即使拆行或加分隔符，也看不出每行代表什么含义**。拆开后依然不知道哪一行是密码、哪一行是邮箱，无法正确做业务处理。
3. **程序无法可靠解析**，容易因格式不一致导致解析失败。

**JSON 的优势**：

1. **自带语义**——用键（key）说明数据含义，用值（value）承载数据，`{"username":"zhangsan"}` 一眼可知。
2. **结构化、严格规范**——是极其严格的数据交换格式，不符合规范就解析失败，保证收发双方理解一致。
3. **跨语言通用**——前端、后端、Agent、插件之间都能解析，是当前数据传递的主流格式（同类还有 xml）。

**出处**：第3章-03-智能体常见的设置 → 3.5.1 文本传输的弊端、3.5.2 什么是 JSON

### 7. 【插件】为什么在 Coze 中需要插件？举两个插件解决大模型弊端的例子。

**答案**

**原因**：大模型本身只能对话，无法直接调用外部工具，数据也不及时（没有实时信息）。要让它真正做事，就必须给它加"手脚"。

> 简单理解：**大模型是大脑，插件是手脚。**

插件也叫做外部工具，是智能体的一部分。

**两个例子**：

1. **天气查询（墨迹天气插件）**——解决"大模型查不到实时天气"的问题。提问"今天北京的天气如何"，智能体调用墨迹天气拿到真实天气数据，再组织回复。
2. **获取当前时间（当前时间插件）**——解决"大模型不知道现在几点、今天几号"的问题。加上时间插件后，用户问"今天的天气怎么样"才能被正确理解。

（其他可用例子：城际路线查询解决实时路况、景点百科解决专业景点信息。）

**解析**：插件使用时要注意它的**输入参数**——比如墨迹天气需要城市和时间，所以要么写在系统提示词里，要么由用户提示词给出，要么由另一个插件获取。这三条是准备插件数据的固定思路。

**出处**：第3章-03-智能体常见的设置 → 3.4.1 插件、3.4.1.4 插件的输入

### 8. 【提示词】用户提示词和系统提示词分别是什么？提取数据时如何命中？

**答案**

**系统提示词**：也就是"人设与回复逻辑"，用来设定模型扮演的身份、任务、规则和回复风格。在 Coze 智能体页面最左侧编写，写一次长期生效。

**用户提示词**：也就是"当前聊天的话"，是用户本轮真正发给模型的内容，在右侧对话框中输入。

每次交互时，**Coze 会把系统提示词和用户提示词合并后一起发给大模型**，不需要手动拼接。这也说明智能体并没有改变大模型健忘的特点，只是帮着它记住。

**提取数据时如何"命中"**：

在系统提示词里把要提取的字段用 `{}` 声明出来，并在节点的「输出数据」中定义**同名变量**，同时要求模型以 JSON 格式返回。模型输出 JSON 后，各字段就能被后续节点精准引用。

课件原文示例（提取人名、工号、绩效）：

```text
你是一个人名提取助手，能够根据用户输入的内容，提取出来里面的人名{name}、
工号{work_code}、绩效{performance_level}，以json格式返回
```

输出数据即为 `name`、`work_code`、`performance_level` 三个变量，后续数据库节点直接引用。

**解析**：`{}` 起的是"字段占位声明"的作用；配合 JSON 输出，字段名与变量名一一对应，才不会出现"提取到了但取不到值"的情况。用户提示词侧则用 `{{input}}` 这类写法引用上游变量。

**出处**：第3章-03 → 3.2 Coze 中的提示词；第5章-03-Coze中的数据库 → 2.3.5 新增数据（字段提取示例）；第4章-03 → 3.1.1.4 设置模型提示词（`{{input}}` 用法）

### 9. 【数据库】Coze 中数据库和知识库的主要区别？各举一个适合使用数据库的业务场景。

**答案**

| | 知识库（Knowledge Base） | 数据库（Database） |
|---|---|---|
| 定位 | 大模型的**补充知识**，存放大模型不知道的内容 | **业务数据**的持久化存储 |
| 操作 | 一般只做**查询**，很少改动 | 支持**增、删、改、查** |
| 内容 | 法律条文、公司手册、产品文档等 | 用户信息、订单记录、绩效数据等 |
| 变化频率 | 低，相对静态 | 高，操作频繁 |

一句话记：**知识库是大模型的"参考资料"，数据库是业务的"账本"。**

**适合用数据库的场景**（任举一个即可）：

1. **用户账号体系**——保存用户名、密码、手机号、邮箱，需要随时注册、修改、注销。
2. **订单管理**——电商订单记录需要持续新增、改状态、删除。
3. **员工绩效/工号台账**——按工号增删改查绩效等级。
4. **图书管理**——按图书编号查询、新增、修改价格与出版社、删除记录。

**解析**：课件里法律咨询项目的例子很典型——法律条文放知识库（供检索），用户的用户名、密码、聊天记录放数据库（供增删改查）。

**出处**：第5章-02-数据库 → 1.4 数据库和知识库的区别

### 10. 【工作流】循环节点的循环方式有几种？区别是什么？各自的应用场景？

**答案**

一共**三种**：

| 循环方式 | 区别 | 应用场景 |
|---|---|---|
| **使用数组循环** | 按传入数组的元素个数循环，几个数据就循环几次 | 前面传入了多个数据，如 `["张三","李四","王五"]`，要逐个人处理；批量生成多个主题的文案 |
| **指定循环次数** | 次数固定，不管什么情况都循环指定的次数 | 次数已知的重复动作，如固定夸奖 3 次、固定重试 5 次 |
| **无限循环** | 字面是永远停不下来，实际是在满足条件时让循环结束 | 不知道循环次数、也不是数组形式，如持续搜集数据直到凑够为止 |

**解析**：循环节点由两部分组成——上面的**循环控制节点**负责控制次数、接收和输出数据；下面的**循环体节点**负责每次循环的具体业务。

循环的意义不只是"重复"，更重要的是**任务拆分**：一次性处理 3 个文案，质量会随数据量增大而下降；拆成 3 次各处理 1 个，效果更好。

**出处**：第5章-05-循环结构 → 4.2 循环快速入门、4.3 案例：文案生成；第5章-06-循环高级 → 5.2 无限循环

### 11. 【工作流】循环节点的"中间变量"有什么作用？简述累加计算的执行流程。

**答案**

**作用**：循环默认**每一次都是互相独立的**。如果某次循环需要依赖前一次的结果，就要用中间变量（临时变量）把每次的计算结果存下来，在多次循环之间传递、累积。

**累加计算（1+2+3+4+5）的执行流程**：

1. **定义中间变量 temp，初始值为 0**（循环开始前）。
2. 第 1 次循环：取出数组元素 1，大模型计算 `1 + temp(0)`，用**设置变量节点**把结果写回 temp，temp 变为 1。
3. 第 2 次循环：取出 2，计算 `2 + temp(1)`，写回 temp，temp 变为 3。
4. 第 3 次循环：取出 3，计算 `3 + temp(3)`，写回 temp，temp 变为 6。
5. 依次类推，最后 temp 记录 15。
6. **输出数据关联中间变量 temp**，循环结束后输出累加结果 15。

**关键配置**：
- 开始节点变量类型选 `Array - Integer`（数组，元素为整数）
- 循环设置选「使用数组循环」，输入数据关联开始节点的数组
- 中间变量：整数，初始 0
- 循环体内两个节点：**大模型节点**负责加法计算（用户提示词写 `第一个值：{{num}}`、`第二个值：{{temp}}`），**设置变量节点**负责把结果写回 temp

**出处**：第5章-06-循环高级 → 5.1 循环的中间变量

### 12. 【工作流】工作流中大模型节点主要的作用是什么？

**答案**

大模型节点可以**结合大模型的推理能力，主打处理自然语言**，还可以给它配置必要的技能，完成推理性的处理任务或数学计算。

具体作用可归纳为：

1. **自然语言理解与生成**——理解用户输入、生成回复内容。
2. **推理与决策**——多步推理、方案规划、条件判断。
3. **信息提取**——从一段自然语言中抽取结构化字段（如人名、工号、价格）。
4. **文本整理与润色**——把生硬或杂乱的检索结果、数据库结果整理成可读的话术。
5. **数学计算**——借助模型完成加减等计算。
6. **可挂技能**——通过「技能」的 `+` 号添加**插件、知识库、其他工作流**，让节点具备查实时数据、查资料的能力。

**输入输出配置**：输入分「输入」（文本）和「视觉理解输入」（图片）；输出可指定格式（如 JSON）。

**出处**：第4章-03-工作流常见的节点 → 3.1 大模型节点

### 13. 【知识库】知识库的检索方式有哪三种？分别的特点？

**答案**

知识库检索节点（以及智能体里的知识库）的搜索策略有三种：

| 检索方式 | 特点 | 举例 |
|---|---|---|
| **全文** | 精准搜索，按字面匹配，只找**同时包含**查询词的文档 | 搜"苹果好吃"，只返回同时包含"苹果"和"好吃"两个词的文档 |
| **语义** | 语义泛化，**能理解近义词**，能处理模糊或复杂问题 | 搜"如何应对失眠？"，能找到关于"改善睡眠质量"的文章 |
| **混合** | 两者兼顾，兼顾字面精准与语义泛化 | 一般场景的稳妥选择 |

**相关参数**（同样影响检索效果）：
- **最大召回数量**：最多返回多少片段，数值越大返回内容越多。
- **最小匹配度**：片段与查询的匹配程度。**越小越泛化，越大越精准**。设得过低会召回大量噪音（如用"连接"匹配到"蓝牙鼠标连接失败"）。

**出处**：第4章-03-工作流常见的节点 → 3.2.6.4 在工作流中创建知识库检索节点

### 14. 【知识库】文档知识库的分段策略与清洗策略分别有哪些？

**答案**

**一、文档解析策略（先于分段设置）**

| 策略 | 说明 |
|---|---|
| **精准解析** | 支持从文档中提取图片元素、扫描件（OCR）、表格元素；支持按文档页粒度过滤不需要导入的内容。耗时更长 |
| **快速解析** | 不支持提取图像、表格等元素，适用于纯文本。速度快 |

选择口诀：**文档里有表格、图片就选精准解析；纯文字就选快速解析。**

**二、分段策略（课件明确讲授两种）**

| 策略 | 说明 |
|---|---|
| **自动分段和清洗** | 根据原始的段落进行拆分 |

### 15. 【工作流】选择器节点和意图识别节点的区别是什么？

**答案**

| | 选择器节点 | 意图识别节点 |
|---|---|---|
| 本质 | **if-else 节点**，按设定的**条件**分支 | 基于**自然语言**的意图分类节点 |
| 判断依据 | 变量的比较结果（为空、等于、大于等），可多条件并用"而且/或者"组合 | 由大模型理解用户说的话，归入预设的某个意图 |
| 输入要求 | 输入必须是**结构化、可比较**的值（如字符串、数字、布尔） | 输入是**用户的自然语言原话** |
| 适用 | 判断参数是否为空、数值范围、状态值等确定条件 | 判断"用户想干什么"（查数据/新增/闲聊/投诉等） |
| 灵活性 | 规则写死，条件必须穷举 | 能处理同义表达、模糊表达 |

**一句话**：选择器是"按条件走分支"，意图识别是"按说话的意思走分支"；**意图识别是基于大模型做场景分类**。

**职责分工的典型用法**：先用意图识别把用户的话分流到"查询/新增/修改/删除/其他"，再用选择器在某个分支内判断必填字段是否为空。

**出处**：第4章-03-工作流常见的节点 → 3.2.1 选择器节点、3.2.2 意图识别节点
